## 2. Fault-count definitions (stem vs branch)
- Classical test literature: SOURCED (search results, lecture notes, not primary texts): under single stuck-at, faults on fanout stems are distinguished from faults on fanout branches; a stem fault is not equivalent to its branch faults; primary inputs and fanout branches are "checkpoints"; equivalence collapsing is local to fanout-free regions; totals depend on collapsed vs uncollapsed, checkpoint vs all sites. URLs: https://ece-research.unm.edu/jimp/vlsi_test/slides/html/faults1.html , https://faculty.kfupm.edu.sa/COE/amindin/Rich/Lect04_Fault_Collapse.pdf , https://ocw.tudelft.nl/wp-content/uploads/Module_3_Fault_Modeling.pdf , https://my.ece.utah.edu/~kalla/ECE6745/atpg_fault_collapsing_msf.pdf . Search summary: "no single authoritative definition of the counting convention".
- Security FI verifiers: FIRMER counts per gate, at most once per gate, no stem/branch notion (SOURCED, arXiv html above). SYNFI replaces gate functions (R10 FULLTEXT), also gate-level. So the security tools I checked count GATE-OUTPUT faults, which is stem-like; branch-only faults (one fanout leg) are not separately modelled in FIRMER. SYNFI/FIVER/VerFI: branch treatment UNVERIFIED.
- Assessment: "fault counts depend on stem/branch/collapsing" is STANDARD in classical test (SOURCED). That a SECURITY redundancy verdict (min faults to defeat a check) changes with the counting convention: I found no source discussing it; UNVERIFIED, absence of hits only, "nothing established as new". Honest framing: known concept, applied to a different question.
- Convention ambiguity: unclear from sources whether per-gate-output (security tools) or stem+branch (test tradition) is "accepted" for security; say both exist.

## 3. Synthesis merges redundancy; mitigations
- SYNFI (R10 FULLTEXT) is the primary security source: Yosys optimisation weakened an FSM (3->2 faults), register merging halved Hamming distance, fixed by set_dont_touch / nofsm. Unchanged.
- OpenTitan commit "[prim_xilinx] Replace KEEP with DONT_TOUCH attributes" SOURCED (https://opensecura.googlesource.com/3p/lowrisc/opentitan/+/cb56b467022a58683cdbf5589cc7a8a7c15944a6): KEEP "previously used to prevent synthesis optimizations across these primitives"; DONT_TOUCH is forward-annotated to place and route; attributes unsupported on module ports, apply to the module. Commit touches the AES yosys_run_synth.tcl (content not seen). Search summary says the commit's purpose was keeping FI and SCA countermeasures; the fetched message text itself does not name them (I saw only the snippet claim): treat as SNIPPET.
- AMD UG901 KEEP vs DONT_TOUCH, KEEP does not stop place-and-route optimisation (https://docs.amd.com/r/en-US/ug901-vivado-synthesis/DONT_TOUCH) SOURCED (snippet). Caveat from same: attribute preserves a signal, not necessarily the surrounding redundant structure (search summary's own inference, UNVERIFIED).
- OpenTitan prim_sec_anchor_* primitives appear in coverage reports (SNIPPET only); their purpose (anchor cells shielding sec_cm logic) UNVERIFIED, docs not read.
- Standard mitigations seen: keep/dont_touch attributes, hierarchy preservation, post-synthesis netlist verification (SYNFI, k-FRP operate on netlists), nofsm. Yosys `keep` attribute behaviour in 0.33 is not verified by this round.

## 4. What our toolkit can defensibly add (honest, not a novelty claim)
1. A small, self-contained, pip+Yosys, plain-language reproducible flow with logged MEASURED results; SYNFI/k-FRP/FIRMER need larger setups (k-FRP needs C++/CMake/Docker; SYNFI needs OpenTitan flow). Usability, not science.
2. Explicit side-by-side of the same circuit under different fault-count conventions (stem vs branch vs per-gate) and netlists, with verdicts; I found no source doing this for a security min-fault question (UNVERIFIED absence).
3. Cross-version/flow synthesis variation (Yosys 0.33 vs other), systematic; SYNFI shows individual cases only (R10).
4. Time-varying free-input min-fault results on a boot-gate FSM with explicit assumptions (goal, input nets, init state), including counterexamples (boot_ok 1-flip break, CT-1).
5. Independent re-derivation of known qualitative results (small check against published behaviour); value is as a cross-check only.
Not defensible: unbounded-proof novelty (k-FRP overlaps; unread), min-search novelty (outer loop over FIRMER/SYNFI budget), secure-boot case study novelty (k-FRP, SYNFI lifecycle, VerifyPIN).
