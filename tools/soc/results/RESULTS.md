## lowRISC Ibex demo system

A small microcontroller-style chip built around lowRISC's Ibex RISC-V processor: 128 kB of RAM, a serial port, general-purpose pins, PWM outputs, an SPI port, a timer and a JTAG debug module through which a debugger can halt the processor and run its own code. The "lockstep" variant switches on Ibex's security configuration: a second copy of the processor runs two cycles behind the first and an alarm fires when they disagree.

Source: https://github.com/lowRISC/ibex-demo-system, commit `d37beb753e19482eb054aefac73a27289bf72e47`, licence Apache-2.0.

### What this says, in plain words

- lockstep, goal "The two processor copies disagree and the alarm stays silent": 3 fault(s) needed (BOUNDED) within 6 cycles.
- lockstep, goal "The processor enters debug mode while the debug port is idle, and no alarm fires": 1 fault(s) needed (BOUNDED) within 10 cycles.
- stock, goal "The processor enters debug mode while the debug port is idle": 1 fault(s) needed (BOUNDED) within 6 cycles.
- Slicing: the smallest slice is 32630 of 43554 cells (74.92 % of the chip, goal debug_entry); the largest is 59423 of 67641 cells (87.9 %, goal debug_entry_silent). Every goal here sits on a processor register, so within a few cycles most of the chip can influence it: slicing helps little and the search runs on most of the chip.
- Cross-check: in 3 of 3 goal/netlist combinations the whole-chip simulation campaign (every cell flipped in every cycle, sampled inputs) agrees with the exact minimum within T cycles: single-fault successes appear exactly where that minimum is 1.
- lockstep, countermeasure "alarm alert_minor_o": REMOVED (flat: REMOVED). Deliberate alarm, constant 0 in this configuration by design: its only source is the instruction-cache ECC and the demo system has no instruction cache. Not a synthesis loss.

### Read with care

- The lockstep variant was configured by source edits for this study: SecureIbex was switched on and the alarm outputs were brought to ports in the fetched copy (chips/ibex_demo/fetch.sh lists both edits). lowRISC does not ship the demo system in this form, so its results describe this configuration, not a lowRISC product.
- "Debug mode" here means the debug-mode register of the processor is set. One flip of that register (or of the controller state in front of it) does this; it is not the same as a debugger being attached, but code that runs with this register set has debug privileges.
- The lockstep alarm compares the outputs of the two processor copies, not their internal state, and it is not armed in the first cycles after reset. The one-fault result on the lockstep chip uses both facts: the flip happens right after reset and the outputs of the two copies do not differ within the ten cycles analysed. It does not say that the alarm would stay silent for longer.
- The RAM is a black box and most data registers have no reset, so the solver chooses their contents. The attacks reported were replayed with those chosen contents; with a specific program in memory the attacker may need more.

## PicoSoC with a boot check

PicoSoC is a small complete computer on a chip: a 32-bit RISC-V processor (PicoRV32), 1 kB of RAM, a serial port and a controller that reads the program from an external SPI flash chip. It has no security features of its own, so a boot check was added in front of it (rtl/bootcheck.v): the whole chip stays in reset until an 8-bit authorisation value on the `sig` pins equals a key.

Source: https://github.com/YosysHQ/picorv32, commit `ef203c2b0a3fb793280f5114941416c425c5b461`, licence ISC.

### Read with care

- The boot check is this project's addition, not part of PicoSoC. Its `sig` pins stand for the verdict of an image verifier that PicoSoC does not have.
